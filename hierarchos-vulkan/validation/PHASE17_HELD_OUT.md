# Phase XVII held-out generalization — 2026-11-10

Phase XVI established that the deterministic full-parameter model can fit its
training fixture. It did not establish that training improves predictions on
unseen data. This phase adds a leakage-resistant, document-level fixture, a
forward-only evaluation path over the real Vulkan graph, and a source-bound
receipt that reports validation and untouched-test loss rather than training
loss.

- Source revision: `5cd0c0c6eb7f` (clean tree). The harness source and binary are

- Harness: `src/bin/held_out_eval.rs`.
- Receipt: `validation/release_parity/multimodal_training/20261110-phase17-heldout-generalization/`.
- Device: AMD Radeon Graphics (Ryzen Z1 Extreme, `1002:15bf`).

## Phase I — audit of the Phase XVI fixture

The fixture the earlier qualification trained on is one synthetic generator
family: 32 rows of `(base + step * 7 + index) % range`. The committed audit
(`validation/fixtures/phase17/phase16_dataset_audit.json`) derives, from the
sealed bytes (`0c5d3e90…`):

| Property | Value |
| --- | ---: |
| Examples | 32 |
| Independent source documents | 1 |
| Tokens | 2,048 |
| Unique examples | 32 |
| Exact duplicates | 0 |
| Near-duplicate pairs (8-gram containment) | 245 |
| Distinct arithmetic offset sets | 2 |
| Batch × steps at the Phase XVI schedule | 8 × 100 = 800 draws |
| Mean reuse per example | 25.0× |

Every row is a cyclic shift of the same progression, so any partition leaks the
held-out distribution and the schedule revisits each example about 25 times.
**Verdict: the original fixture cannot support a meaningful held-out split.**
It remains frozen and is still the numerical/dispatch fixture; the audit is
bound to the Phase XVI stability receipt's `fixture.dataset_sha256`.

## Phase II — the Phase XVII fixture

A separate versioned corpus lives in `validation/fixtures/phase17` and is
generated by `validation/make_phase17_fixture.py` with the standard library
only, so it reproduces on a checkout without numpy.

- 320 independent documents across three grammar families (`catalog`,
  `schedule`, `log`), 40 lines each.
- Split at **document** granularity by
  `sha256("20261110:" + document_id)`: first 80% train, next 10% validation,
  remaining 10% test.
- The vocabulary is built from the **training partition only** (568 words +
  4 specials, `vocab.json`), then applied to every partition.
- Held-out documents are deterministically regenerated (same id, next attempt)
  until no 8-gram occurs in another partition, so cross-partition contamination
  is zero **by construction**, not by tolerance.
- Windows never cross a document boundary and the final short window carries an
  explicit valid-token count.

| Partition | Documents | Tokens | Windows | Supervised targets |
| --- | ---: | ---: | ---: | ---: |
| train | 256 | 136,616 | 2,304 | 136,360 |
| validation | 32 | 17,112 | 288 | 17,080 |
| test | 32 | 17,272 | 288 | 17,240 |

The 100-step / batch-8 schedule draws 800 of 2,304 training windows, so no
training example is repeated within the run.

## Phase III — forward-only evaluation

`VulkanTransformer::forward_logits` is the read-only evaluation entry point: it
takes `&self`, so the borrow checker statically excludes parameter, moment,
optimizer-step and dropout-seed mutation, and it disables every configured
dropout site. `held_out_eval` computes causal cross-entropy on the host from
those logits with a stable log-sum-exp in f64, target alignment
`logit[t] → token[t+1]`, token weighting over valid (non-padding) targets, and a
padded final batch that contributes nothing.

Every evaluation records parameter and optimizer-state digests, the optimizer
step, the dropout seed, and WMMA phase deltas before and after. All twelve
evaluations per arm (and every control) show identical digests and zero
weight-gradient or input-gradient dispatches. FP32 evaluations dispatch no
cooperative GEMM; mixed evaluations dispatch only the forward phase.

The *observable* optimizer-state digest covers step, learning rate, AdamW
coefficients and dropout seed. Full-parameter moment tensors are private, so
the receipt states that limitation and proves the moments were untouched
behaviourally instead: a 20-step run with an evaluation interleaved at step 10
is bitwise identical, in every loss bit, every parameter digest and the final
model, to the same 20-step run with no evaluation. This holds for both an FP32
and a mixed two-pass arm.

## Phases IV–VII — results

Fixed protocol: LR `1e-3`, AdamW `(0.9, 0.999, 1e-8)`, weight decay `0`,
batch 8, sequence 64, 100 steps, validation at steps 0/10/20/40/60/80/100. The
test partition is read exactly twice per arm (step 0 and step 100); no
hyperparameter was selected from it.

Initial loss is at the uniform-vocabulary scale (ln 1024 ≈ 6.93, and the model
vocabulary is 1024), so the starting point is uninformative and the final loss
is far below it. Test and validation track each other (2.822 vs 2.832 for A),
and both continue to fall through step 100; this is not a case of training loss
improving while held-out loss deteriorates.

### Numerical contracts

- A/B: every loss bit, per-step parameter digest, update norm and dispatch
  counter is identical, and the final parameter digests match.
- C/D: the same bitwise identity holds independently under mixed WMMA.
- FP32 versus mixed drift is reported separately: first-step `2.5e-05`,
  maximum `0.8689`, RMS `0.1948`, final `0.1918`; final validation gap `0.0942`.
  The first step is inside the declared `2e-2` policy; the later spread is
  chaotic trajectory divergence, not a per-step contract failure.
- Dispatch: scalar arms show exactly `200` scalar backward dispatches (2 layers
  × 100 steps) and zero query/key; two-pass arms show `200` query + `200` key
  and zero scalar. Evaluation adds none.

### Seed investigation (Phase VI)

Seeds 7, 13 and 21 produce bitwise-identical full-parameter trajectories.
The seed is **not an active randomness source here**: dropout is `0.0`,
initialization comes from the frozen checkpoint, dataset order is a
deterministic function of the step index, and no LoRA is involved. Identical
trajectories are therefore not independent replication.

For meaningful replication the receipt varies a source that is genuinely active:
the training-window order. Two 100-step runs at offsets 37 and 512 reach
validation `3.006` / `2.975` and test `3.009` / `3.031`, against `2.832` /
`2.822` for the declared order. The held-out improvement is therefore robust to
order, with a spread of roughly ±3% in final loss — and the declared run is the
best of the three, which is reported rather than hidden.

### Generalization versus memorization

The evidence is consistent with learning the two-family grammar, not with
memorizing documents: held-out documents are 8-gram disjoint from training
documents and were regenerated to stay that way, vocabulary is training-only,
and test loss falls by 60%. Per-family final test loss (arm A): `log` 2.313,
`schedule` 2.835, `catalog` 3.519. The claim is scoped to this synthetic
three-family corpus; it is **not** broad language-model generalization.

## Verification

```powershell
cargo build --release --bin held_out_eval
python validation/qualify_heldout_phase17.py --install
python validation/check_heldout_phase17.py
python -m unittest discover -s validation -p "test_heldout_phase17.py"
```

The checker regenerates the fixture from its committed generator and requires
byte identity, re-derives every window stream and causal alignment, re-sums the
token-weighted losses, recomputes perplexity and drift, and re-verifies the
read-only, dispatch, leakage and seed controls. It does not trust `pass` fields.

The 22 controls reject, each for its intended reason: duplicate training
documents in validation and in test, cross-partition 8-gram overlap, a wrong
split identifier, an altered dataset hash, a changed tokenizer identity, a
forged valid-token count, padding counted as loss, wrong causal alignment,
tampered validation and test loss, a missing evaluation, parameters changed by
evaluation, an optimizer step advanced by evaluation, a missing arm, scalar
fallback mislabeled as two-pass, a tampered dispatch profile, an invalid binary
hash, an unrelated source revision, a missing evidence artifact, a
validation-only result presented as test evidence, and non-reproducible fixture
bytes.

## Remaining limits

- The fixture is synthetic and narrow; the generalization claim is scoped to it.
- Full-parameter AdamW moments are not publicly readable; the receipt records
  that and covers them with the bitwise interleaved-evaluation control.
- Evaluation cross-entropy is computed on the host from `forward_logits`, not by
  the training cross-entropy shader.
- Mixed WMMA remains opt-in; the device scope is this AMD RDNA3 machine.
- CPU CI re-verifies committed evidence; it does not re-execute GPU workloads.
