# Phase XIX — post-promotion rebaseline and the attention scratch-reuse experiment

**Status: GO — CANDIDATE WORTHS A SEPARATE PROMOTION REVIEW.**

Candidate A (reuse of the query-backward intermediate score, probability and `dp`
through the two scratch planes the pass already owns) was re-evaluated against
the **Phase XVIII promoted** dQ-unroll shader rather than the Phase XVII one. It
is **bitwise identical** to the promoted shader on every compared tensor, and it
improves the complete step by **7.1 %–14.8 %** with a 95 % confidence interval
excluding 1.0 in all eight measured series and every round of every series.

The experiment artifact is **not** promoted. It lives only in this receipt, has
no production identity, and no production dispatch, selector, gate, default or
tolerance was changed. Phase XVIII's promoted implementation remains the
production default.

## 4. Candidate A: design, before any code

### 4.1 What the promoted shader actually does

After the visibility scan, the promoted pass-1 body traverses the key range four
times. Each traversal recomputes the 128-wide `Q·K` dot product; two of them also
recompute the 128-wide value dot:

| traversal | score dot | value dot | exp | K reads for the dQ outer product |
| --- | :-: | :-: | :-: | :-: |
| 2 — row maximum | ✓ | | | |
| 3 — normaliser | ✓ | | ✓ | |
| 4 — `softmax_dot` / `kv_softmax_dot` | ✓ | ✓ | ✓ | |
| 5 — dQ adjoint (specialized) | ✓ | ✓ | ✓ | ✓ |

So per key: **4 score dots, 2 value dots, 3 exponentials** — of which *3 score
dots and 1 value dot are pure recomputation* of a value already computed in the
same invocation. Only the final probability and the final dS leave the
invocation; the intermediates are discarded because the promotion moved the
128-float accumulator into VGPRs and left no private storage to hold a key range.

### 4.2 The proposed reuse

Keep three intermediates in the two planes the pass already writes, and drop the
recomputation:

| slot | written | read | overwritten |
| --- | --- | --- | --- |
| `scratch_probability[slot]` | raw score (traversal 2) | traversals 3, 4 | final `p` (traversal 4) |
| `scratch_ds[slot]` | `dp` (traversal 4) | traversal 5 | final `p·(dp − kv_dot)` (traversal 5) |

Expected static change per key per lane, on the admitted 128/128 geometry:

| quantity | promoted | candidate | delta |
| --- | ---: | ---: | ---: |
| FMA (dots + outer product) | 768 | 256 | **−512 (−67 %)** |
| q/k/grad-out/v buffer reads | 1,664 | 640 | **−1,024 (−62 %)** |
| exponentials | 3 | 2 | **−1 (−33 %)** |
| scratch accesses | 2 stores | 4 stores + 4 loads | **+6** |

Per invocation on the seq64 causal fixture (mean 32.5 visible keys per row):
−16,640 FMA, −33,280 buffer reads, −32.5 exponentials, +195 scratch accesses. Per
complete step (2 layers × 1,024 pass-1 invocations): **−34.1 M FMA, −68.2 M
buffer reads, −66.6 K exponentials, +399 K scratch accesses**. These are static
counts from the source, not hardware performance counters.

### 4.3 Traffic and synchronization verdict — proceed, no barrier

The added traffic is **three orders of magnitude smaller than the traffic it
replaces**: 8 scratch accesses per key against 1,024 buffer reads per key. The
scratch planes are 1 MiB per step in total, already written once per key by the
control, and already resident in cache after the first traversal.

Synchronization requirement: **none beyond program order.**

* `scratch_base = (batch·heads + head) · q_seq · kv_seq + query · kv_seq`, so one
  invocation owns exactly one row of both planes for its whole lifetime. No two
  invocations address the same slot.
* All four traversals touch `[0, last_key]` under the same `key_visible`
  predicate, so every read is preceded by a write in the same invocation on the
  same lane. No read can observe a previous dispatch's or a previous step's
  contents — the reused slot is *always* written first in this invocation.
* The masked-row and no-visible-key early returns run **before** the caching
  traversals and clear `[0, last_key]` of both planes, exactly as the control
  does, so masked-row semantics and scratch initialisation are unchanged.
* No cross-lane access, no subgroup operation, no barrier, no new
  inter-dispatch visibility. Pass 2 still consumes the planes after this
  dispatch completes, which is the existing ordering.
* The four traversals are the *same* four traversals as the control — the loop
  count does not change, only the work inside each. No extra pass over the key
  range is introduced.

No scope or risk finding blocked the implementation.

### 4.4 Arithmetic-order analysis

Storing a `float` to a `float32` storage buffer and loading it back is exact, and
the cached value is the identical 32-bit result the control recomputes from
identical inputs in identical association order. Therefore every downstream
expression:

* `attention_exp(s - max_score)` — same `s`, same `max_score`;
* `p = attention_exp(...) * inv_sum` — same operands;
* `ds_q = p · (dp − softmax_dot)` — same `p`, same `dp`, same `softmax_dot`;
* `p · (dp − kv_dot)`, `p · dp`, `softmax_dot += p·dp`, the `precise` mode-9 tree
  `score_scale = (pc.scale · 1.0) · ds_q`, and the literal-index accumulator
  macros `QX_ACC0` / `QX_ACC9` — untouched.

**No arithmetic change, so no changed comparison was required and no tolerance
was touched.** The two softmax-dot reductions remain distinct (`softmax_dot`
plain → dQ; `kv_softmax_dot` precise → dS/dK/dV) and keep their existing
consumers; `kv_dot` still selects between them by `unfused_qk`. The only
*statement* difference is that the final `p` store moved from traversal 5 to
traversal 4 and the final dS store now overwrites the cached `dp` in traversal 5
— same address, same final value.

### 7.3 Isolated pass-1 kernel timing (mechanism)

`raw/33_kernel_timing.log`, GPU timestamps, no profiler, 5 ABBA rounds × 8
repeats, 1024 rows / 16 workgroups:

| mode | promoted (ms/dispatch) | candidate (ms/dispatch) | median ratio | speedup |
| --- | ---: | ---: | ---: | ---: |
| 0 | 2.083–2.612 (round 0: 3.607) | 1.364–1.955 | **0.654** | **1.53×** |
| 9 | 2.487–2.558 | 1.412–1.434 | **0.569** | **1.76×** |

Mode 0's round-0 promoted sample is an outlier (3.607 ms, the first round after
pipeline creation); the median over five rounds is used and every round improves.
The isolated kernel saving is **0.72 ms/dispatch** in mode 0 and **1.08
ms/dispatch** in mode 9, i.e. **1.44–2.16 ms per complete step** for two
dispatches.

That brackets the measured complete-step saving (1.94–2.28 ms on the sequence-64
fixtures) from below and is consistent with it; in Mixed mode 9 it predicts it
almost exactly. It is **not** a predictor in general: the isolated harness repeats
one dispatch against warm buffers, which flatters the promoted arm's four
redundant traversals more than a full step does, so the isolated ratio understates
the complete-step gain in FP32 mode 0. Reported for mechanism, not as a claim.

## 10. Limitations

1. **Parity matrix is helper-level for 13 of 28 cases.** Non-causal and
   sequence-≠-64 grouped configurations are rejected before pass 1 by the
   pre-existing grouped gate in a real step (§6.1). Full-route evidence is the two
   in-graph runs and the step counters, not those rows.
2. **Write coverage is not independently measured.** Both arms pre-fill every
   output and scratch slot with the same sentinel, so the comparison proves the
   two shaders agree everywhere it compares; it cannot distinguish a slot both
   leave at the sentinel from one both write identically.
3. **No AMD ISA dump exists on this host** (`RadeonGPUAnalyzer`/`amdllvm` absent),
   so register residency is not re-derived here. The claim made is the SPIR-V one
   (§5) — the accumulator still has 128 constant-index chains — not a VGPR
   statement about the candidate.
4. **The attribution in §3 is profiler-instrumented.** Stride-1 sampling perturbs
   execution; only §7 is a performance measurement. The profiled GPU total exceeds
   the unprofiled step by ~25 %, which is why no cross-section arithmetic is done.
5. **Weight-mirror conversion is zero *per step*, not proven zero at load.** The
   profiler cannot see work before the first measured step (§3.3).
6. **Sequence 128 for 8q/2kv and 4q/2kv is not measured.** The pre-existing grouped
   qualification admits sequence 64 only, so the production step never reaches
   either pass-1 shader there; Phase XVIII documented the same exclusion and this
   phase does not widen the gate.
7. **Two unused GPU allocations remain in the test-only timing helper**
   (`phase_xix_median_ms` allocates `grad_k`/`grad_v` that pass 1 does not bind),
   producing two `unused_variable` warnings in the test build. They are outside the
   timed region and affect no measurement; they were left in place rather than
   rebuilding the binary that produced this receipt.
8. **Round 0 of the isolated kernel timing** contains a promoted-arm outlier; the
   five-round median is reported and every round still improves (§7.3).
9. **Effect-size interpretation.** The 7.1 %–14.8 % range spans four fixtures of
   very different step cost; nothing here is pooled, and the largest relative
   effects are on the smallest steps (4q/2kv sequence 64), where the query pass is
   the largest share of the step.
