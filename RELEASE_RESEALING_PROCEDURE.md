# Unified release resealing and qualification procedure

This document records the procedure actually executed for the RDNA3 scoped release
across Phases XXIV–XXVI, and centres on the reseal that produced
`hierarchos-vulkan/validation/release_parity/multimodal_training/20261115-phase25-current-source`.
It is derived from the scripts, workflows and receipts in this repository; every
command below was run in that form.

The rule this procedure exists to enforce: **a receipt may only be regenerated by
executing its producer against the source and binaries being qualified.** Rewriting
a digest, copying an older receipt into a newer root, or relaxing a threshold is not
resealing, and none of those were done.

## 1. Establish the starting state

```bash
git rev-parse HEAD origin/codex/rdna3-phase19-instrumented   # must match
git status --porcelain --untracked-files=no                  # must be empty
```

Every assembler opens with the same guard:

- `qualify_phase19x_current.py`, `qualify_phase19y_full_attention.py`,
  `qualify_phase19z_current.py`, `qualify_packed_current.py` and
  `qualify_unified_release.py` refuse to run on a dirty tracked worktree
  (`--allow-dirty` exists on the first two but is not used for a release).
- Receipt installers refuse to overwrite: `qualify_attention_phase19x.py`,
  `qualify_training_phase16.py`, `qualify_training_stability.py`,
  `qualify_heldout_phase17.py`, `qualify_wmma_drift.py`,
  `qualify_activation_phase19x.py` and `qualify_unified_release.py` all fail when
  the destination exists.
- Checkers accept a receipt from any root that is an **ancestor** of `HEAD`
  (`git merge-base --is-ancestor`), so a receipt produced at revision R stays
  valid after the evidence commit R+1.

Free space matters: the packed-cell rebuild plus two archive extractions peaked at
425 MB free in Phase XXV. Check before starting:

```bash
powershell -NoProfile -Command "'{0:N0} MB free' -f ((Get-PSDrive C).Free/1MB)"
```

Never free space by deleting `hierarchos-vulkan/target/release/*.exe`, the pinned
interpreter at `target/unified-oracle/Scripts/python.exe`, the frozen fixture trees,
the oracle archives, or any `release_parity` root. Scratch directories only, after
their results are installed into a receipt.

## 2. Map the dependency graph before changing anything

Each component binds three things: the source inventory, the executable digest, and
the fixture manifest. Read the producer, not a summary of it:

| Question | Where the answer lives |
|---|---|
| Which sources are bound? | `source_inventory()` / `EXTRA_SOURCES` / `VALIDATION_SOURCES` in the producer |
| Which executable is bound? | the producer's `--binary`/`--bins` argument, or `binaries` in the input map |
| Which fixtures? | `--fixtures`, `--shape-fixtures`, `--shared-fixtures`, `--fixture` |
| Where does the receipt go? | `RECEIPT`, `RECEIPT_DIR`, `RECEIPT_ROOT`, or `--output` |
| Can it be redirected for staging? | `HIERARCHOS_RECEIPT_DIR` or `--output`; the XIX-X/Z assemblers hardcode the root |

Two properties of this codebase drive the whole procedure:

1. `qualify_phase19x_current.py` and `qualify_phase19z_current.py` compute their root
   from `Path(__file__)`, so the root is a **source fact**, not a flag. Changing it
   changes the file, which changes the receipt's `source_files` digest. The root must
   therefore be advanced **before** any receipt is generated in it.
2. `check_unified_release.py` validates each component's recorded `binary_sha256`
   against the `binaries` map of the input file, and the map's digest against the file
   on disk. Any executable rebuilt after a component ran invalidates that component.

A component may be reused only when its recorded executable digest equals the current
binary digest and its fixture manifests still match. Otherwise it is regenerated.

## 3. Advance the root without overwriting history

The 2026-11-15 reseal moved
`20261112-unified-release` → `20261115-phase25-current-source` as one coordinated
change: assemblers, checkers, unified release, negative controls, both workflows and
the completion document all name the root literally.

Apply it as a **byte-exact** replacement:

```bash
python - <<'PY'
old = b'20261112-unified-release'
new = b'20261115-phase25-current-source'
for name in FILES:                      # the 20 files listed by grep, below
    data = open(name, 'rb').read()
    if old in data:
        open(name, 'wb').write(data.replace(old, new))
PY
```

Find the affected files with:

```bash
grep -rln 20261112-unified-release --include=*.py --include=*.yml --include=*.md \
  hierarchos-vulkan/validation/*.py .github/workflows *.md
```

Do **not** use `sed -i` for this. On Windows it rewrites CRLF as LF, which turned a
21-line change into a 4,034-line diff in Phase XXV; the change was reverted and redone
as a binary replacement (79 insertions / 79 deletions across 20 files). Commit this
migration alone, before generating evidence, so the new receipts bind the final source.

Leave every older root in place. Historical receipts are the record of what was
qualified then, including receipts that no longer describe the current source.

### The attention parser defect

`validation/emit_two_pass_evidence.py` originally matched the case line with
`^\[(?P<case>…)`. libtest prints `test <name> ... ` **without a trailing newline**, so
the first case's `eprintln!` is appended to that status line. The anchor therefore
dropped exactly one record: `fixture-causal` reported 2 of 3 tensors and the producer
failed with *"expected 12 gradient comparisons, found 11"* while the test itself passed
with `test result: ok. 1 passed`.

The fix removes only the line-start anchor; every numeric field of the pattern is
still matched exactly. `check_attention_phase19x.py` re-derives the counts from the
same raw log through `parse()`, so producer and verifier agree by construction, and
`test_phase19x_current.py` still rejects a receipt whose `comparisons` is 11. After the
fix the producer reports `PASS (<rev>, 12 tensors, 3158064 elements)` with every tensor
bitwise equal. Do not "fix" this by widening tolerances or by accepting 11.

The oversized-fallback fixture is the frozen 128-wide package, not the 2x24 tree.
`wmma_shape_profitable` now requires `rows * columns * reduction >=
WMMA_MIN_PROFITABLE_MACS` (16,000,000) before a cooperative executor exists at
all, so at 48 rows (`48 * 128 * 128 = 786,432`) every projection is declined by
the crossover policy and the Full FP16 reduction cap is never consulted — the
diagnostic would silently stop proving a fallback. Build the fixture from the
frozen tree instead, keeping the model bytes untouched:

```python
import json, shutil
src, dst = Path('target/unified-precision-fixture'), Path('target/phase38-fallback128-fixture')
shutil.copytree(src / 'model', dst / 'model')            # byte-identical 128-wide package
d = json.loads((src / 'input.json').read_text())
d['batch_size'] = d['image_count'] = 48                  # 1,152 rows, one image per sequence
for k in ('input_ids', 'attention_mask', 'targets', 'loss_weights'):
    d[k] = d[k] * 24                                     # frozen 2x24 block, repeated 24x
d['rgb'] *= 24; d['alternate_rgb'] *= 24                 # 48 images x 768 bytes
```

`1,152 * 128 * 128 = 18,874,368` clears the floor, so all seven projections are
admitted and the reduction cap decides: 64 is below the forward/input-gradient
reduction of 128 and the weight-gradient reduction of 1,152. The producer
asserts the derived route count (`7 * 7 + 2 * 2 * 7 = 77` fallbacks), zero
cooperative dispatches and zero Full FP16 accumulations. Do not restore the
2x24 tree, and do not relax the count to `> 0`.

The `seq2seq` wide fixture root is `unified-wide-seq2seq-cpu-3`; the similarly named
`-cpu` directory is a partial tree without `manifest.json`.

### Native V4.1 cooperative geometry (open conflict)

The native V4.1 fixtures must be generated with the pinned oracle **and**
`ATEN_CPU_CAPABILITY=avx2` (plus `MKL_ENABLE_INSTRUCTIONS=AVX2`,
`ONEDNN_MAX_CPU_ISA=AVX2`): on this AVX512 host the same torch build emits
different kernels, and `prepare_v41_wmma_fixture.py --weight-std .02
--upstream-std .003` then stops reproducing `unified-v41-bounded-fixture.json`
byte-for-byte (`11 0a049473aa…` for the stress shape, `46e46f6eb733…` for the
bounded one).

`qualify_v41_wmma.py` needs `accumulation_dispatches[0] > 0`, so the vision
tower must clear `WMMA_MIN_PROFITABLE_MACS`. The historical 8x8 fixture cannot:
16 patches × 384 columns × 128 reduction = 786,432. Three cooperative
geometries were measured, and each one breaches the fixture's own bounded
`max_abs < 2e-7` FP32 limit:

| geometry | gate | `projected` population | measured FP32 max |
|---|---|---|---|
| 40×40 image, 400 patches | 19.66 MMAC | 12,800 | 3.58e-7 |
| 12×12 image + 4096 MLP, 36 patches | 18.87 MMAC | 1,152 | 2.38e-7 |
| 8×8 image + 8192 MLP, 16 patches | 16.78 MMAC | 512 | 3.05e-7 |

Raising the patch count multiplies the compared population (extreme-value
growth of the absolute maximum); widening the MLP raises the activation
magnitudes, and the limit is absolute. Do not "fix" this by lowering
`--weight-std`, by widening the tolerance, or by dropping the bounded label.
The owner decision is either a cooperative native-vision geometry whose
absolute FP32 error stays under 2e-7, or an explicit statement that the bounded
strict comparison is taken at the released (sub-crossover) geometry and the
cooperative route is qualified by the separate primitive component.

## 11. Hosted workflows

All four must conclude on the **exact** final commit; a run from an earlier commit is
not evidence about the later one.

| Workflow | File | Gate |
|---|---|---|
| Phase XIX-W architecture compatibility | `architecture-compatibility.yml` | `test_phase19w_compatibility.py` over the committed matrix |
| Phase XIX-Y oracle bytes | `phase19y-oracles.yml` | downloads the pinned archives and re-verifies byte-for-byte |
| Phase XIX instrumented qualification | `phase19-instrumented.yml` | `check_activation_phase19x.py` via `HIERARCHOS_ACTIVATION_RECEIPT` |
| Workspace check | `workspace-check.yml` | compile, suites, Phase XIX-X, unified release, fault injection |

```bash
gh run list --branch codex/rdna3-phase19-instrumented --limit 8
gh run view <id> --log-failed
```

Two failure modes seen in practice are evidence problems, not numerical ones, and were
fixed at the cause:

- The compatibility matrix must exist in the active root; reissue it with
  `phase19w_matrix.py --forward … --generation … --peft … --output <root>/phase19w-matrix.json`
  from the frozen captures.

A matrix is source-bound twice: its `source_contract` (eight digests, one of them
its own builder) and its `registry_source_sha256`. Both are verified with
`source_provenance` against the revision the matrix declares, not against the
checkout. A sealed matrix is a statement about one revision, exactly like the
unified receipt that carries it, so a later release that touches
`hierarchos-vulkan/src/transformer.rs` must not make either artefact expire — and
reverifying against the running bytes would also invalidate every matrix as soon
as the verifier itself is corrected, because the builder hashes itself. The
architecture inventory is still read from the current tree by `validate()`, and
`check_unified_release.py` additionally requires the matrix's declared revision to
be an ancestor of the receipt's `source_revision` — the same lineage rule the
receipt's own source map uses. Sealing applies the same ancestry rule, so a matrix
from an unrelated revision is refused rather than silently re-certified; a matrix
is carried forward only while the current registry still parses to its inventory.
- `.gitignore` excludes `*.safetensors`, so LoRA adapter evidence is present in the
  worktree but absent from every checkout. Use `git add -f` for
  `release_parity/**` and confirm tracked count equals on-disk count before pushing.

The self-hosted `time-mix-ab.yml` (packed-cell producer A/B) requires
`runs-on: [self-hosted, windows, vulkan]` with a tuned `linear3-forward` /
`linear-residual-forward` module. With no such runner registered the job stays queued
and is never a pass. It is not a blocker for the scoped RDNA3 release, which is
measured locally on the qualified adapter by `qualify_packed_current.py`.

## 12. Evidence integrity invariants

A receipt is only as good as the files its pointers resolve to. Two invariants follow
from the Phase XV audit (`PHASE15_EVIDENCE_REBINDING_AUDIT.md`):

1. **Every digest must resolve to a committed blob at the receipt's revision.** Check it
   before committing a root:

```bash
python - <<'PY'
import json,subprocess
R='hierarchos-vulkan/validation/release_parity/multimodal_training/<root>'
d=json.load(open(R+'/current-qualification.json'))
digs=[v['qualification_sha256'] for v in d.get('retained',{}).values()]+list(d.get('evidence',{}).values())
print(subprocess.run(['git','cat-file','--batch-check'],input='\n'.join(digs),capture_output=True,text=True).stdout)
PY
```

   Every line must report `blob`, not `missing`. A digest that resolves to nothing means
   the run's output was never preserved and the receipt cannot support it.
2. **Regeneration produces a new root; it never rewrites an old receipt in place.** An
   in-place edit that changes `source_head`, a binary digest or a numeric leaves the
   historical root describing a run it did not record, and no amount of refreshing
   `SHA256SUMS` makes it provenance again.

Note that `verify.py` in the Phase XV root does not check the `evidence` map or the
`retained.*.qualification_sha256` values, so a root can pass its own verifier while
those pointers are broken. Run both checks above and the root verifier.

### The digest guard

`hierarchos-vulkan/validation/check_evidence_integrity.py` is the executable form of
both invariants. It is offline and deterministic: it reads receipts, hashes raw file
bytes (never a re-serialized copy of the JSON), and resolves every declared binding.

```bash
# one root, fail closed
python hierarchos-vulkan/validation/check_evidence_integrity.py --root \
  hierarchos-vulkan/validation/release_parity/multimodal_training/<root> --strict

# the newest sealed release, which is what CI gates on
python hierarchos-vulkan/validation/check_evidence_integrity.py --latest-release --strict

# every digest-declaring root, report only (historical audit)
python hierarchos-vulkan/validation/check_evidence_integrity.py --audit-all
```

Bindings it understands: `evidence` and `evidence_files` maps, `retained.*.qualification_sha256`,
`components[*].{path,sha256}`, and `sources`/`source_files`. A metadata block such as
`{"file": "evidence.zip", "bytes": 21372426}` is not mistaken for a digest map.
Paths are resolved only inside the root (and the repository, for source bindings);
traversal, absolute paths and symlinks that leave the root are rejected.

Statuses are reported separately, never collapsed into one PASS/FAIL:

| Status | Meaning |
|---|---|
| `valid` | bytes hash to the declared digest |
| `mismatch` | a file exists at the declared location but its bytes differ |
| `missing` | no candidate file exists under the root |
| `source-drift` | a bound source changed after the receipt's revision (expected for historical roots, fatal for a release) |
| `invalid-digest` | the declared value is not a SHA-256 |
| `unsafe-path` | the reference escapes the root |
| `unsupported-schema` | the receipt declares no binding this guard understands |
| `provenance-unestablished` | the digest may be correct, but no executable, log or producer artifact is tracked, so a run cannot be shown |

`--strict` fails on everything except `provenance-unestablished`, which is reported
because no repository convention guarantees a preserved log. That is the honest split:
a matching hash proves bytes, not execution.

When the guard has to run: before a root is committed, and as the `evidence integrity`
workflow runs it on every push against the newest sealed release. Strict scope is the
release's own dependency closure; historical roots are covered by `--audit-all`, so a
known defect in an old root cannot silently fail an unrelated release — and cannot be
hidden either, because `test_evidence_integrity.py` asserts that the Phase XV
rebinding is still detected.

Negative controls live in `test_evidence_integrity.py` (18 tests): byte change, digest
change, removal, aggregate/family disagreement, retained-digest disagreement, malformed
digest, traversal, escaping symlink, unsupported schema, Git-object absence versus
mismatch, source drift, provenance separation, the current release passing strict, and
the Phase XV regression with two mutation controls that prove the suite fails if the
evidence-map check or digest resolution is disabled.

## 13. Evidence provenance vocabulary

Every claim in a handoff must name which of these it is:

- **Executed** — a producer ran in this reseal against the current source and binaries;
  the receipt records the revision and executable digest.
- **Reused** — not re-run, but its recorded executable digest and fixture manifests
  still match the current build, and its source revision is an ancestor of `HEAD`.
- **Historical** — sealed once, no longer bound to the current source (for example the
  19 architecture-specific shared-image entries, or Gen9 captures).
- **Pending** — not produced at all: physical Gen9, RDNA1/RDNA2, AVX2-host, and the
  self-hosted packed-cell A/B.

A scoped statement such as `PASS_SCOPED_RELEASE` describes RDNA3 with the documented
precision policy; it does not extend to unmeasured devices.
